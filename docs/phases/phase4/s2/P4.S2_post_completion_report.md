## 2. Scope Delivered

### 2.1 Workstream A — Snapshot Contract (§5)

**Deliverable:** `packages/domain/snapshot.py` (416 lines)

- `EvaluationStatus` enum with four values: `SUCCESS`, `INSUFFICIENT_EVIDENCE`, `PARTIAL_FAILURE`, `FAILED`.
- `IntelligenceSnapshot` frozen dataclass carrying the full evaluation payload (health, anomaly, diagnostic, finding, telemetry window, evaluation duration, errors, contract version, metadata, persisted-at marker).

### 2.2 Workstream B — Persistence + Evaluation Lifecycle (§6)

**Deliverables:**

- `packages/domain/repository.py` — `IntelligenceSnapshotRepository` abstract base class (`save`, `get_latest`, `get_latest_for_fleet`, `get_history`, `get_by_id`) and in-memory implementation `InMemorySnapshotRepository`.
- `apps/backend/migrations.py` — new table `aegis_intelligence_snapshots` with 18 columns, two composite indexes (`idx_snapshot_device_eval`, `idx_snapshot_asset_eval`), JSONB storage for nested intelligence objects, and foreign key to `aegis_devices`.
- `apps/backend/postgres_adapter.py` — `PostgresSnapshotRepository` implementing the ABC against PostgreSQL. Uses `ON CONFLICT DO NOTHING` for idempotent writes and `DISTINCT ON (device_id)` for efficient fleet latest-snapshot retrieval.
- `apps/backend/evaluation_service.py` (294 lines) — `IntelligenceEvaluationService` orchestrating the four-stage pipeline (Health → Anomaly → Diagnostic → Risk). Public API: `evaluate_asset()` and `evaluate_fleet()`. Each stage is wrapped in `_run_stage()` for error isolation; a stage failure degrades the snapshot to `PARTIAL_FAILURE` rather than crashing the lifecycle.

### 2.3 Workstream C — Fleet / Asset Query Integration (§7)

### 2.5 Out-of-Scope Additions (justified)

Two deliverables were added beyond the specification during live-run verification. Both are isolated to `scripts/` and do not alter domain, intelligence, or repository packages.

- `scripts/live_simulator.py` — continuous synthetic telemetry streamer for all four seeded devices (two pumps, two ESP32 nodes). Pre-seeds 15 baseline ticks, then streams 2-second ticks and runs `evaluate_fleet(persist=True)` each tick.

## 4. Problems Encountered and Mitigations

This section documents every non-trivial issue that arose during implementation, the root cause analysis, and the resolution. These are the signals a senior reviewer should scrutinize.

### 4.1 PowerShell UTF-8 Encoding Corruption

**Symptom:** `Get-Content` returned mangled characters for files containing box-drawing or non-ASCII characters (`─` became `Ã¢â€â€`), causing silent corruption when files were rewritten.

**Root cause:** Windows PowerShell defaults to the system code page (CP-1252 or OEM) rather than UTF-8 for both input and output. Reading a UTF-8 file through `Get-Content` and writing it back through `Set-Content` double-encodes the stream.

**Mitigation:** All file I/O was moved to `[System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)` and `[System.IO.File]::WriteAllText($path, $content, [System.Text.Encoding]::UTF8)`. Console output was pinned with `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`. No further encoding corruption occurred after this change.

**Lesson for codebase:** any future tooling that touches source files from PowerShell must use the .NET I/O APIs directly, not cmdlets.

### 4.2 Migration Verification Failure: `KeyError: 0`

**Symptom:** The post-migration verification query raised `KeyError: 0` when accessing `cur.fetchone()[0]`.

**Root cause:** `PostgresConnectionPool` is configured with `row_factory=dict_row`, which makes `cur.fetchone()` return a `dict` keyed by column name, not a tuple. Integer indexing is a type error, not a value error.

**Mitigation:** All downstream code accessing cursor rows uses `row["column_name"]` consistently. This was audited across `postgres_adapter.py` and verified by the full test suite.

### 4.3 `operational_state` and `health_score` Missing from Serialized Snapshots

**Symptom:** `PostgresSnapshotRepository.save()` was persisting `operational_state = "UNKNOWN"` even for snapshots that clearly reported `NORMAL` or `DEGRADING`.

**Root cause:** `IntelligenceSnapshot.operational_state` is a `@property` derived from `self.health.operational_state`, not a dataclass field. Serialization via `asdict()` or the custom `to_dict()` did not include properties. The database write was reading `data.get("operational_state", "UNKNOWN")` from the serialized dict, which always returned the default.

**Mitigation:** Changed the write path to pull directly from the snapshot object: `snapshot.operational_state.value` and `snapshot.health.health_score`. The same bug would have occurred for any other derived property; added a code comment flagging that serialization does not include computed properties.

**Lesson:** derived properties on frozen dataclasses are a correct design choice for in-memory objects, but every persistence boundary must read them explicitly, not through serialization.

### 4.4 Cyclomatic Complexity (C901) on `evaluate_asset`

**Symptom:** Ruff flagged `evaluate_asset` with complexity 11, exceeding the project threshold of 10.

**First attempted mitigation (failed):** A PowerShell regex `Replace()` call attempted to insert helper methods and partition the method body. The replacement silently failed because the regex did not account for exact whitespace, leaving the file unchanged.

**Second attempted mitigation (failed):** A Python regex rewrite was invoked. It successfully modified `evaluate_asset` but mangled the indentation of the adjacent `evaluate_fleet` method at line 251, breaking the file.

**Final mitigation (successful):** `evaluation_service.py` was fully rewritten from a clean Python heredoc, splitting the pipeline into five single-responsibility methods: `_run_pipeline_stages()`, `_run_diagnostic()`, `_run_risk()`, `_run_stage()`, `_persist_snapshot()`. Complexity dropped to 6 on each. All 12 lifecycle tests pass unchanged.

**Lesson:** regex-based source edits are unsafe for whitespace-sensitive languages. For any non-trivial refactor, a clean file rewrite is faster and more auditable than incremental patching.

### 4.5 Test Assertion Logic Error: `is_complete` on Empty Telemetry

**Symptom:** The test `test_evaluate_asset_with_insufficient_telemetry` asserted `not result.snapshot.is_complete` and failed.

**Root cause:** The intelligence services (`HealthAssessmentService`, `AnomalyDetectionService`, etc.) return valid frozen dataclass objects even when telemetry is empty — they return `UNKNOWN` state with `health_score = 0.0`. All four pipeline stages therefore "succeed" from the lifecycle's perspective, and `is_complete` (which checks whether all four stages produced an object) correctly returns `True`.

**Mitigation:** The test was corrected to assert the actual honesty guarantee: `is_healthy == False` and `health_score == 0.0`. The `is_complete` property reflects pipeline execution completeness, not evidential sufficiency. This distinction is now documented in the snapshot module docstring.

**Lesson:** `is_complete` and `is_healthy` are orthogonal predicates. A snapshot can be complete (all stages ran) but unhealthy (insufficient evidence). The naming is accurate but requires care at the test boundary.

### 4.6 Neon Cloud Database Exhausted

**Symptom:** Mid-sprint, all PostgreSQL operations began timing out against the Neon free-tier instance.

**Root cause:** Neon free trial compute allocation was exhausted. The connection string in `.streamlit/secrets.toml` was still valid but the backend was suspended.

**Mitigation:** Switched to a local Docker PostgreSQL instance (`aegis-postgres`, port 5434). Backed up Neon configuration to `secrets.toml.neon-backup` for later restoration. Discovered during inspection that the Neon URL was present in git history at commit `d5ec2d2 docs(sprint8)` — the secrets file itself is correctly gitignored, but the URL leaked through a documentation commit. Flagged for secret rotation on cloud restoration.

**Follow-up action required:** rotate the Neon credential before any public branch publication. The URL in commit `d5ec2d2` should be considered compromised.

### 4.7 Connection Pool Exhaustion During C-MAPSS Device Registration

**Symptom:** `scripts/stream_cmapss_db.py` hung for ten seconds then failed with `couldn't get a connection after 10.00 sec`.

**Root cause investigation path:**

1. First suspicion: idle-in-transaction sessions holding pool slots. Verified via `pg_stat_activity` — no idle sessions.
2. Second suspicion: `PostgresDeviceRegistry.register_device()` opens a connection per device via `_get_conn()`. With five devices and 21 sensors each, this is 110 connection checkouts in rapid succession.
3. Actual root cause: `register_dataset_assets()` was instantiating a *second* `PostgresDeviceRegistry` with `PostgresDeviceRegistry(db_url)`, which constructed a *second* internal connection pool against the same database. The two pools competed for the database's connection slots, and the first pool (owned by the streamer) was already holding its connection open across the registration call via `with pool.connection() as conn:`.

**Mitigation sequence:**

1. First attempt: added `pool: PostgresConnectionPool | None = None` parameter to `register_dataset_assets()` so the caller could pass an existing pool. This surfaced the deeper issue — the inner `PostgresDeviceRegistry` was still creating its own pool unless explicitly given one.
2. Second attempt: added a `get_device("engine-001")` check to short-circuit if devices are already registered. This mitigated the symptom on second runs but did not fix the first run.
3. Final mitigation: `apps/dataset_replay/registration.py` was rewritten to use a direct `psycopg.connect(db_url, row_factory=dict_row)` for the registration transaction, bypassing the pool entirely. Registration is a one-shot bootstrap operation; it has no need for pooled connection reuse. The main streaming loop continues to use the shared pool. Registration now completes in under 200 ms with a single transaction containing two `executemany` calls (devices then sensors).

**Lesson:** connection pool ownership must be explicit at every boundary. Any component that silently constructs its own pool against a shared resource is a latent deadlock. A code audit of all `PostgresConnectionPool(...)` constructors is recommended.

### 4.8 Dashboard Time-Series Chart Rendering Months of Flat Data

**Symptom:** The Telemetry History chart showed a nearly flat line stretched across ten months of x-axis labels (Jan through Oct), with a visible spike only at the far right edge.

**Root cause:** `PostgresTelemetryRepository.get_observations()` returns results ordered `ASC` with `LIMIT 1000`. The database contained ~1600 historical seed rows dated January 2026 plus a few hundred live rows dated October 2026. `LIMIT 1000 ORDER BY timestamp ASC` returned only the January seed data, missing the active live stream entirely.

**Mitigation:** The dashboard's Telemetry History tab was updated to fetch the most recent 200 observations, sorted chronologically for display. The repository method was not changed to preserve backward compatibility. The database was also truncated of the stale seed rows (`TRUNCATE aegis_telemetry_observations CASCADE`) so the live simulator could demonstrate real-time chart motion.

**Lesson:** `LIMIT` on a time-ordered table without a time filter is a correctness bug waiting to happen. Consider adding a required `since: datetime` parameter to `get_observations()` in a future sprint, or at minimum defaulting the sort to `DESC` for "most recent" semantics.

### 4.9 Frozen Dataclass Mutation Attempt in Live Simulator

**Symptom:** `scripts/live_simulator.py` raised `dataclasses.FrozenInstanceError: cannot assign to field 'timestamp'` when attempting to retime synthetic observations to wall-clock.

**Root cause:** `Observation` is a frozen dataclass. The simulator was generating observations with simulated timestamps and then trying to overwrite `.timestamp` with `datetime.now(UTC)`.

**Mitigation:** Used `dataclasses.replace(obs, timestamp=now)` to produce a new frozen instance with the updated timestamp. This is the canonical pattern for frozen dataclass updates and preserves immutability.

### 4.10 Minor Ruff / Format Issues

Ruff requires the name to be importable at module scope even when annotations are lazy at runtime.
- `I001` import ordering after adding the snapshot import — auto-fixed by `ruff check --fix`.
- `E501` line length violations in log strings — resolved by extracting local variables for the long interpolations.

## 6. Known Limitations and Follow-Up Items

The following items are explicitly out of scope for P4.S2 but should be tracked for future sprints.

1. **Neon credential rotation** — the connection URL present in commit `d5ec2d2` must be invalidated before any public branch publication.
2. **`get_observations()` default ordering** — the current `ORDER BY timestamp ASC LIMIT 1000` is a correctness hazard for time-series queries without an explicit window. Candidate for a safe API migration in a future sprint.
3. **Connection pool ownership audit** — a repository-wide grep for `PostgresConnectionPool(` turned up several callers that construct their own pools against the shared database. Not a defect in P4.S2, but a latent risk flagged by the registration-time deadlock.
4. **Snapshot history retention policy** — the `aegis_intelligence_snapshots` table has no TTL. Snapshots accumulate indefinitely. A retention sweep (e.g., keep last N per device, or last 30 days) should be designed before any production deployment.
5. **Snapshot contract versioning** — `SNAPSHOT_CONTRACT_VERSION = "v1"` is set but no migration path exists for `v2`. A documented upgrade strategy should accompany any future snapshot schema change.
6. **Dashboard auto-refresh backpressure** — if the auto-refresh interval is set shorter than the fleet evaluation duration, the dashboard will queue overlapping evaluations. A simple mutex or last-evaluation-timestamp guard would prevent this.
